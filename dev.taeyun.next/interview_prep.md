# Next.js 포트폴리오 프로젝트 예상 면접 질문 및 답변 (Node.js 전문가 관점)

이 문서는 Next.js로 개발된 포트폴리오 웹사이트 프로젝트에 대해, Node.js 전문가를 채용하는 면접에서 나올 수 있는 예상 질문과 답변을 정리한 것입니다.

---

### 1. 프로젝트 개요 (Project Overview)

**질문:** 이 프로젝트에 대해 간략하게 설명해주시겠어요? 어떤 목적으로 만들어졌나요?

**답변:**
이 프로젝트는 저의 기술 스택, 경력, 그리고 수행했던 프로젝트들을 소개하기 위해 만든 개인 포트폴리오 웹사이트입니다. Next.js를 사용하여 개발되었으며, 인터랙티브한 UI와 애니메이션을 통해 사용자 경험을 높이는 데 중점을 두었습니다. 방문자들이 저의 역량을 시각적으로 흥미롭게 파악할 수 있도록 기획했습니다.

---

### 2. 기술 스택 (Technical Stack)

**질문:** 이 프로젝트에서 사용된 주요 기술 스택은 무엇이며, 왜 해당 기술들을 선택했나요?

**답변:**
*   **프레임워크:** Next.js (React 기반)
*   **언어:** TypeScript
*   **스타일링:** Styled-components, Sass
*   **애니메이션:** GSAP, Lottie
*   **빌드/개발:** Next.js CLI, Webpack (내장), Babel (내장), ESLint

**선택 이유:**
*   **Next.js:** 서버사이드 렌더링(SSR)과 정적 사이트 생성(SSG)을 모두 지원하여 초기 로딩 성능과 SEO 최적화에 유리하기 때문에 선택했습니다. 또한, Node.js 기반으로 동작하므로 Node.js 생태계의 이점을 활용할 수 있었습니다.
*   **TypeScript:** 대규모 애플리케이션으로 확장될 가능성을 염두에 두고, 정적 타이핑을 통해 코드의 안정성과 유지보수성을 높이기 위해 도입했습니다.
*   **Styled-components:** 컴포넌트 기반 스타일링을 통해 재사용성을 높이고, CSS-in-JS의 장점을 활용하여 동적 스타일링을 쉽게 구현하기 위해 사용했습니다.

### 3. 아키텍처 및 Node.js 관련 질문 (Architecture & Node.js Specifics)

**질문:** 이 프로젝트에서 Node.js는 어떤 역할을 하나요? API 서버를 직접 구축하셨나요?

**답변:**
이 프로젝트는 별도의 커스텀 API 서버를 구축하지는 않았습니다. 대신 Next.js 프레임워크가 내부적으로 사용하는 Node.js 서버에 의존합니다. 구체적으로 Node.js는 다음과 같은 역할을 수행합니다.

1.  **개발 환경 서버:** `next dev` 스크립트를 실행할 때, Node.js 기반의 개발 서버가 Hot Module Replacement (HMR)와 같은 기능을 제공합니다.
2.  **프로덕션 서버:** `next build` 후 `next start`를 실행하면, Node.js 서버가 빌드된 정적 파일들을 서빙하고, 필요한 경우 서버사이드 렌더링을 수행합니다.
3.  **서버사이드 렌더링(SSR) 및 정적 사이트 생성(SSG):** 페이지 요청 시 서버에서 React 컴포넌트를 HTML로 렌더링하거나, 빌드 타임에 미리 HTML을 생성하는 역할을 Node.js 환경에서 수행합니다. 이를 통해 클라이언트의 부담을 줄이고 초기 렌더링 속도를 개선합니다.
4.  **빌드 프로세스:** `next build` 과정에서 Webpack, Babel과 같은 Node.js 기반의 도구들이 TypeScript 코드를 컴파일하고, 번들링하며, 최적화하는 작업을 수행합니다.

**질문:** `package.json`을 보니 `pages/api` 디렉토리가 없는 것 같습니다. 만약 이력서 파일을 다운로드하는 기능을 추가해야 한다면 어떻게 구현하시겠어요?

**답변:**
두 가지 방법이 있습니다.

1.  **Public 디렉토리 활용 (현재 구조):** 이력서 파일을 `public` 디렉토리에 위치시키고, 간단한 `<a>` 태그의 `download` 속성을 이용해 직접 다운로드 링크를 제공하는 방법이 가장 간단합니다.
2.  **API Route 구현:** 만약 다운로드 횟수를 로깅하거나, 특정 권한이 있는 사용자에게만 다운로드를 허용하는 등의 로직이 필요하다면 `pages/api/download.ts`와 같은 API Route를 생성하겠습니다. 이 API Route는 Node.js 환경에서 실행되며, `fs` 모듈을 사용해 서버에 저장된 파일을 읽고, `res.setHeader()`를 통해 적절한 `Content-Disposition` 헤더를 설정하여 파일 다운로드를 트리거할 수 있습니다.

**질문:** `next.config.js`에서 `@next/bundle-analyzer`를 설정한 것을 확인했습니다. 번들 크기를 분석하고 최적화하기 위해 어떤 조치를 취했거나, 취할 수 있을까요?

**답변:**
`@next/bundle-analyzer`는 프로덕션 빌드 후 생성되는 JavaScript 번들의 크기를 시각적으로 분석하여, 어떤 라이브러리가 많은 용량을 차지하는지 파악하는 데 사용했습니다. 이를 통해 다음과 같은 최적화를 진행했거나, 할 수 있습니다.

1.  **Dynamic Imports (동적 로딩):** 초기 페이지 로딩에 필수적이지 않은 무거운 컴포넌트나 라이브러리(예: Lottie 애니메이션, 특정 섹션)를 `next/dynamic`을 사용하여 사용자가 해당 영역으로 스크롤하거나 특정 상호작용을 할 때 비동기적으로 로드하도록 구현할 수 있습니다.
2.  **라이브러리 대체:** 번들 분석 결과, 특정 기능에 비해 과도하게 큰 라이브러리를 사용하고 있다면, 더 가벼운 대안(예: moment.js 대신 day.js)을 찾아 교체하는 것을 고려할 수 있습니다.
3.  **Webpack 설정 커스텀:** `next.config.js`의 Webpack 설정을 직접 수정하여 코드 스플리팅(Code Splitting) 전략을 더 세밀하게 조정하거나, 사용하지 않는 코드를 제거(Tree Shaking)하는 플러그인을 추가할 수 있습니다. (Next.js가 기본적으로 제공하지만, 추가 설정이 필요할 수 있습니다.)

**질문:** 이 Next.js 애플리케이션을 어떻게 프로덕션 환경에 배포하시겠어요? Node.js 관점에서 고려할 점은 무엇인가요?

**답변:**
Vercel을 이용하는 것이 가장 간단하고 효율적인 방법이지만, 직접 Node.js 서버 환경에 배포하는 시나리오를 가정하고 답변드리겠습니다.

1.  **빌드:** 먼저 `package.json`의 `build` 스크립트(`next build`)를 실행하여 `.next` 디렉토리에 프로덕션용 빌드 결과물을 생성합니다.
2.  **Node.js 서버 실행:** 빌드 후 `next start` 스크립트를 실행하면 `.next` 디렉토리를 기반으로 최적화된 Node.js 서버가 실행됩니다.
3.  **프로세스 매니저 사용:** 실제 운영 환경에서는 예기치 않은 오류로 서버가 다운될 경우를 대비해 `PM2`와 같은 프로세스 매니저를 사용하여 `next start` 프로세스를 실행하고 모니터링해야 합니다. 이를 통해 서버 다운 시 자동으로 재시작하고, 멀티 코어 CPU를 활용한 클러스터 모드를 운영하여 성능을 극대화할 수 있습니다.
4.  **환경 변수 관리:** 데이터베이스 접속 정보나 API 키 등 민감한 정보는 소스코드에 하드코딩하지 않고, `.env` 파일을 사용하거나 서버 실행 환경에서 직접 환경 변수를 주입하여 관리해야 합니다.

**답변:**
(자신의 실제 경험에 맞게 이 부분을 수정하여 준비하는 것이 중요합니다. 아래는 예시입니다.)

**예시 답변:**
초기에는 GSAP와 full-page 스크롤 라이브러리 간의 충돌로 인해 애니메이션이 부자연스럽게 동작하는 문제가 있었습니다. 스크롤 이벤트가 여러 라이브러리에 의해 동시에 제어되면서 race condition이 발생한 것이 원인이었습니다.

이 문제를 해결하기 위해, React의 `useEffect`와 `useState` 훅을 사용하여 스크롤 상태를 통합적으로 관리하는 컴포넌트를 만들었습니다. 특정 섹션이 뷰포트에 들어왔을 때만 GSAP 애니메이션이 트리거되도록 상태를 제어하고, 다른 스크롤 관련 로직은 비활성화하는 방식으로 이벤트 충돌을 막았습니다. 또한, React의 생명주기를 활용하여 컴포넌트가 언마운트될 때 모든 스크롤 이벤트 리스너와 GSAP 인스턴스를 정리(`cleanup`)하도록 하여 메모리 누수를 방지했습니다. 이 과정을 통해 React 컴포넌트의 생명주기와 상태 관리에 대한 이해를 높일 수 있었습니다.
